# SPEC 06 — Migración de la base de datos y las credenciales a Supabase

> **Status:** Borrador
> **Depends on:** SPEC 04, SPEC 05
> **Date:** 2026-10-06
> **Objective:** Migrar las tres tablas de SQLite a Postgres en Supabase y sustituir las credenciales de `.env` por Supabase Auth, dejando la app corriendo igual en local con la sesión por cookie httpOnly.

## Por qué existe este spec

Hoy todos los datos viven en un único fichero local, `data/prices.db`: una sola máquina, sin copias automáticas y sin forma de consultar el histórico desde otro sitio. Si el fichero se pierde, se pierde todo el trabajo del scraping.

Las credenciales de acceso son un par de strings en `.env` comparados con `timingSafeEqual`: no hay usuario real, ni historial de cambios, ni manera de cambiar la contraseña sin tocar el servidor a mano.

Supabase ya ofrece Postgres gestionado y Auth en el mismo proyecto (existe y el esquema `public` está vacío). Migrar datos y credenciales a la vez evita dos transiciones: la API REST, la cookie httpOnly y los guards de SPEC 05 no cambian de forma.

## Scope

**In:**

- `supabase/migrations/0001_esquema_inicial.sql` nuevo: tablas `products`, `pages` y `price_checks` con `bigint generated by default as identity`, `timestamptz`, índices `idx_pages_product` y `idx_checks_page`, el `CHECK` de `status` intacto, RLS activo **sin** políticas en las tres, y la función `reset_sequences()` para ajustar las secuencias tras la migración. Se aplica al proyecto remoto con el MCP (`apply_migration`), dejando el fichero en el repo.
- Dependencia nueva en `server`: `@supabase/supabase-js`.
- `server/src/supabase.ts` nuevo: cliente único (URL + service role key) de creación perezosa, usado por el repo y por Auth.
- `server/src/repo.ts` nuevo: interfaz `Repo` con los métodos que hoy ejecuta `routes.ts`, más los tipos `ProductRow`, `PageRow` y `CheckRow` (movidos de `db.ts`).
- `server/src/repo-supabase.ts` nuevo: implementación de `Repo` sobre supabase-js, con las fechas normalizadas a ISO con `Z`.
- `server/src/app.ts`: `buildApp({ repo, auth })` recibe las dependencias por inyección, con las de producción como valor por defecto.
- `server/src/index.ts`: falla al arrancar con código 1 y mensaje claro si faltan `SUPABASE_URL` o `SUPABASE_SERVICE_ROLE_KEY`.
- `server/src/auth.ts`: puerto `AuthPort` (`signIn`, `refresh`, `signOut`) con implementación sobre Supabase Auth; la sesión sigue siendo cookie httpOnly y el `Map` pasa a guardar `{ accessToken, refreshToken, expiresAt }` de Supabase, refrescando el access token localmente cuando queda menos de 60 s de vida.
- Login con **email**: `routes.ts` valida `{ email, password }` y lo envía a Supabase Auth; el mensaje de error sigue siendo «Usuario o contraseña incorrectos».
- `web/src/pages/Login.tsx`: label «Email», `type="email"`, `autoComplete="email"`; `web/src/api.ts` y `web/src/auth.tsx` pasan `email` en lugar de `username`. El resto de la UI sin cambios.
- `server/scripts/seed-admin.ts` nuevo (+ script npm): crea el usuario admin en Supabase Auth desde `SUPABASE_ADMIN_EMAIL`/`SUPABASE_ADMIN_PASSWORD` del `.env`, sin duplicarlo si ya existe.
- `server/scripts/migrate-from-sqlite.ts` nuevo (+ script npm): copia `products`, `pages` y `price_checks` de `data/prices.db` a Supabase preservando ids y fechas, hace copia de seguridad del fichero, ajusta las secuencias con `reset_sequences()` y verifica los conteos.
- Tests: `api.test.ts` inyecta un repo falso y `auth.test.ts` un auth falso en `buildApp()`; `vitest.config.ts` pierde `DB_PATH`, `ADMIN_USERNAME`, `ADMIN_PASSWORD`, `setup.ts` y `fileParallelism`.
- Borrado de SQLite: `server/src/db.ts`, la implementación SQLite transitoria del repo, `DB_PATH` y `ADMIN_USERNAME`/`ADMIN_PASSWORD` como credenciales de login. `data/prices.db` se conserva como copia.
- Documentación: `README.md` y `AGENTS.md` con las variables nuevas, los scripts y el estado final.

**Out of scope (for future specs):**

- Despliegue del backend o del frontend (hosting, dominio, HTTPS, cookies `Secure`).
- Varios usuarios, roles, recuperación o cambio de contraseña.
- Políticas RLS de lectura anónima (web pública de precios).
- Uso de Realtime, Storage, Edge Functions o Cron de Supabase.
- Tests que hablen con Supabase (red o Docker): los tests siguen mockeando la capa de datos.
- Secretos de Supabase en GitHub Actions: no hacen falta con tests mockeados.
- Cambios en el scraper o en la API REST más allá del payload de login.
- Borrar `data/prices.db`.

## Data model

Esquema en Supabase (`supabase/migrations/0001_esquema_inicial.sql`):

```sql
create table products (
  id bigint generated by default as identity primary key,
  name text not null,
  image_url text,
  created_at timestamptz not null default now()
);

create table pages (
  id bigint generated by default as identity primary key,
  product_id bigint not null references products(id) on delete cascade,
  url text not null,
  store text not null,
  css_selector text,
  created_at timestamptz not null default now()
);
create index idx_pages_product on pages(product_id);

create table price_checks (
  id bigint generated by default as identity primary key,
  page_id bigint not null references pages(id) on delete cascade,
  price double precision,
  currency text,
  status text not null check (status in ('ok','not_found','blocked','error')),
  error_msg text,
  method text,
  checked_at timestamptz not null default now()
);
create index idx_checks_page on price_checks(page_id, checked_at desc);

alter table products enable row level security;   -- sin políticas: solo service_role
alter table pages enable row level security;
alter table price_checks enable row level security;

create function reset_sequences() returns void language sql as $$
  select setval(pg_get_serial_sequence('products','id'), coalesce((select max(id) from products), 1));
  select setval(pg_get_serial_sequence('pages','id'), coalesce((select max(id) from pages), 1));
  select setval(pg_get_serial_sequence('price_checks','id'), coalesce((select max(id) from price_checks), 1));
$$;
```

`by default as identity` permite insertar los ids originales de SQLite; `reset_sequences()` evita que la siguiente inserción normal choque con un id ya usado.

Autenticación:

```ts
// server/src/auth.ts
interface TokenPair { accessToken: string; refreshToken: string; expiresAt: number } // epoch ms
export interface AuthPort {
  signIn(email: string, password: string): Promise<TokenPair | null>;
  refresh(refreshToken: string): Promise<TokenPair | null>;
  signOut(accessToken: string): Promise<void>;
}
const sessions = new Map<string, TokenPair>(); // token de cookie -> tokens de Supabase
// cookie: igual que SPEC 05 (pt_session, httpOnly, SameSite=Lax, Max-Age=604800)
// isValidSession: existe la entrada y no ha caducado; si `expiresAt` está a <60 s, se refresca
```

## Implementation plan

1. `supabase/migrations/0001_esquema_inicial.sql` con el contenido de arriba y aplicación con el MCP (`apply_migration`). Verificación: `list_tables` con `verbose` muestra las tres tablas, los índices y el RLS activo; la app sigue funcionando con SQLite.

2. `@supabase/supabase-js` en `server`, `server/src/supabase.ts` (cliente perezoso con `SUPABASE_URL` y `SUPABASE_SERVICE_ROLE_KEY`) y las cuatro variables nuevas en `.env`. Verificación: `npm run typecheck -w server` en verde; la app aún no usa el cliente.

3. `server/src/repo.ts` con la interfaz y los tipos; el SQL actual pasa a `server/src/repo-sqlite.ts`; `routes.ts` recibe el `Repo` por parámetro y `app.ts`/`index.ts` lo inyectan (por defecto, el de SQLite). Verificación: `npm run verify` en verde y `npm run dev` idéntico al de antes.

4. `server/test/api.test.ts` inyecta un repo falso en `buildApp()`; se eliminan `DB_PATH`, `setup.ts` y `fileParallelism` de `vitest.config.ts` y el fichero `test/setup.ts`. Verificación: `npm test` en verde sin tocar ninguna base y `git status` limpio.

5. `server/src/repo-supabase.ts` con todas las operaciones (fechas normalizadas a `toISOString()`), `index.ts` lo usa por defecto y termina con `exit 1` si faltan las claves. Verificación: `npm run dev` con el `.env` real: crear, editar y borrar productos y páginas desde la UI, con `execute_sql` del MCP confirmando las filas; un `POST /api/pages/:id/check` real inserta su `price_check`.

6. `server/scripts/seed-admin.ts` (+ script npm `seed:admin`) que llama a `auth.admin.createUser` solo si el email no existe. Verificación: ejecutarlo dos veces seguidas; el Dashboard de Supabase muestra un único usuario.

7. `auth.ts` con `AuthPort` y su implementación Supabase (signIn, refresh con menos de 60 s, signOut con revocación), `routes.ts` con el body `{ email, password }`, `auth.test.ts` con un puerto falso, y `ADMIN_USERNAME`/`ADMIN_PASSWORD` fuera de `vitest.config.ts`. Verificación: `curl` con las credenciales del seed → `200` con cookie; con contraseña mala → `401` con el mensaje intacto; `npm test` en verde.

8. `Login.tsx` (label «Email», `type="email"`, `autoComplete="email"`), `api.ts` y `auth.tsx` (payload y firma con `email`). Verificación: `npm run typecheck -w web` en verde y login manual en el navegador con `npm run dev`.

9. `server/scripts/migrate-from-sqlite.ts` (+ script npm `migrate:sqlite`): abre `data/prices.db` en solo lectura, copia de seguridad del fichero, inserta las tres tablas con ids explícitos y fechas convertidas de `YYYY-MM-DD HH:MM:SS` (UTC) a ISO con `Z`, llama a `reset_sequences()` y compara conteos. Verificación: ejecutarlo contra el proyecto real; los tres conteos coinciden; los productos antiguos se ven en `/` y su histórico en `/products/:id`; crear un producto nuevo no produce id duplicado.

10. Borrado de SQLite: `server/src/db.ts`, `server/src/repo-sqlite.ts`, `DB_PATH` y sus referencias en comentarios de `env.ts`/`index.ts`/docs. Verificación: `grep -r "node:sqlite\|DB_PATH\|prices.db" server/src` sin resultados, `npm run verify` en verde y `npm run dev` sin `.env` sale con código 1.

11. Documentación: `README.md` y `AGENTS.md` (variables, scripts `seed:admin` y `migrate:sqlite`, nota de que la BD es Supabase y `data/prices.db` es solo un respaldo). Verificación: `npm run verify` y `npm run build` en verde y cada comando documentado existe en algún `package.json`.

## Decisions

- **Sí:** el backend Fastify es el único cliente de Supabase (service role). **No:** frontend directo con anon key, porque reescribiría la API y pondría RLS a prueba en cada lectura.
- **Sí:** `@supabase/supabase-js` para datos y Auth con una sola dependencia. **No:** `pg` + API de Auth a mano: dos clientes y dos formatos de error que mantener.
- **Sí:** cookie httpOnly del backend con el `Map` en memoria, como en SPEC 05. **No:** sesión de supabase-js en el navegador: expondría access y refresh token a JavaScript.
- **Sí:** validar la sesión localmente por `expiresAt` y refrescar con el refresh token cuando quedan menos de 60 s. **No:** `getUser()` en cada petición: una llamada de red por request y dependencia total de la disponibilidad de Supabase.
- **Sí:** mismo esquema con `bigint generated by default as identity` y `setval` posterior. **No:** UUID: obligaría a reescribir todas las FK y a perder los ids que ya usa el frontend.
- **Sí:** RLS activo sin políticas (solo el service role lo bypasea). **No:** RLS deshabilitado: si en el futuro se usa la anon key, no leería nada por accidente.
- **Sí:** cambiar el label de SPEC 05 de «Admin Username» a «Email», porque Supabase Auth identifica por email; el criterio de ese spec queda sustituido por el de este. **No:** mapear un username a un email fijo en `.env`, que sería magia oculta.
- **Sí:** mantener el mensaje «Usuario o contraseña incorrectos». **No:** «Email o contraseña incorrectos»: los criterios de SPEC 05 siguen ciertos tal cual.
- **Sí:** repositorio y auth como puertos inyectados en `buildApp({ repo, auth })`. **No:** `vi.mock` del cliente, que quedaría acoplado a sus internals; la inyección sigue el patrón de `buildApp()` de SPEC 04.
- **Sí:** `exit 1` en `index.ts` si faltan las claves de Supabase. **No:** arrancar con aviso, como con `ADMIN_*`: sin BD, todas las rutas de datos responden 500 y el error llega tarde.
- **Sí:** corte limpio de SQLite al final del plan, manteniendo `repo-sqlite` solo hasta que `repo-supabase` esté verificado. **No:** fallback por variable de entorno: código muerto después de la migración.
- **Sí:** credenciales del seed en `.env` (`SUPABASE_ADMIN_EMAIL`/`SUPABASE_ADMIN_PASSWORD`), coherente con lo actual. **No:** prompt interactivo ni argumentos de CLI (historial de la shell).
- **Sí:** script de migración propio con ids explícitos, conversión de fechas UTC y `reset_sequences()` vía RPC. **No:** herramientas de migración de Supabase: no migran desde SQLite.
- **Sí:** fechas normalizadas a ISO con `Z` en el repo. **No:** confiar en el formato de PostgREST: `GET /api/products` compara `checked_at` como texto.
- **Sí:** SQL en `supabase/migrations/` aplicado con el MCP. **No:** CLI de Supabase: solo hay entorno remoto y el CLI añade Docker al flujo.
- **Sí:** CI sin secretos de Supabase: los tests usan falsos. **No:** secretos en GitHub Actions que nadie necesita.
- **Sí:** depende de SPEC 04 (`buildApp`, `verify`, suite con inyección) y SPEC 05 (cookie, guards y endpoints de auth).

## Risks

| Riesgo | Mitigación |
| --- | --- |
| El formato de fecha de PostgREST rompe la comparación lexicográfica de `last_check_at` | El repo normaliza a `toISOString()`; se comprueba con el listado de productos tras migrar (paso 9). |
| Tras insertar ids explícitos, la secuencia queda por detrás y crear un producto falla | `reset_sequences()` al final del script y criterio de aceptación con un alta nueva tras migrar. |
| La app local pasa a depender de internet | Aceptado: es el coste de mover la BD a la nube; los errores de red caen en el manejador de errores actual (500 + log). |
| Varias peticiones simultáneas refrescan el token a la vez (rotación de refresh) | El refresco se comparte con una única promesa por sesión; se prueba con dos pestañas en el paso 7. |
| La service role key filtrada da acceso total a la BD | Solo vive en `.env` git-ignored, nunca se importa desde `web/`; criterio sobre el bundle. |
| La BD local cambia mientras corre el script | El script pide parar la app, inserta en una transacción por tabla y verifica conteos al final. |
| `runCheck` deja de escribir al cambiar el repo | Paso 5 con un `/check` real antes de tocar el auth y la migración. |

## What is **not** in this spec

- Despliegue, HTTPS, cookies `Secure` y dominio real.
- Varios usuarios, roles, recuperación o cambio de contraseña.
- Lecturas anónimas con políticas RLS (web pública).
- Realtime, Storage, Edge Functions o Cron de Supabase.
- Tests de red o con Docker contra Supabase; secretos en CI.
- Cambios en el scraper o en la API más allá del payload de login.
- Borrar `data/prices.db`.

Cada uno de esos, si llega algún día, va en su propio spec.
