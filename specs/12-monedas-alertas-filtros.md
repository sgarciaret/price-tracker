# SPEC 12 — Monedas, alertas de precio y filtros de lista

> **Status:** Implementado
> **Depends on:** SPEC 09-precio-mejor-collection.md, SPEC 11-mejor-precio-tienda-detalle.md
> **Date:** 2026-10-12
> **Objective:** Comparar los precios convertidos a una moneda base con tasas de cambio, alertar in-app cuando se cumple un precio objetivo o una bajada porcentual y permitir buscar y filtrar la lista de productos.

## Por qué existe este spec

Hoy la app compara precios crudos sin convertir: un precio de 89 USD "gana" frente a 95 EUR en el resumen, en `insertCheck` y en la tabla del detalle. Además, `price_checks` acumula historial pero no hay ninguna forma de que la app avise de una bajada, y en la lista solo existe ordenación, sin búsqueda. Este spec corrige la comparación entre monedas, añade alertas de precio visibles en la app y busca/filtra la lista de productos.

**Limitación consciente:** las alertas se evalúan solo cuando se ejecuta una comprobación manual ("Comprobar" / "Comprobar todas"), porque las comprobaciones automáticas quedan fuera de este spec.

## Scope

**In:**

- Migración `supabase/migrations/0004_add_best_currency.sql`: columnas `best_currency` en `products` y `pages`.
- Migración `supabase/migrations/0005_price_alerts.sql`: columnas de objetivo en `products`, tabla `price_alerts` e índice; `reset_sequences()` ampliado.
- Módulo FX `server/src/fx.ts`: `FxPort`, `createHttpFx()` (API `https://open.er-api.com/v6/latest/<base>`, caché 24 h, fallback estático), `convert()` y `pickBest()`.
- Inyección de FX en `buildApp({ fx })`, `createSupabaseRepo(client, fx)` y `RoutesOptions.fx`; los tests inyectan tasas fijas (sin red).
- `repo-supabase.ts` y `fake-repo.ts`: mejor precio calculado sobre valores convertidos y guardado con `best_currency`; resumen con `stores`, `last_status` y `unread_alerts`; detalle con `fx`, `best_page_id` y objetivos.
- Módulo `server/src/alerts.ts`: `evaluateAlerts()` pura con las reglas `target` y `drop`.
- Endpoints: `GET /api/alerts`, `POST /api/alerts/:id/read`, `POST /api/alerts/read-all`; `PUT /api/products/:id` ampliado con los objetivos.
- Evaluación de alertas tras cada comprobación y al guardar el objetivo.
- Frontend: tipos `Fx`/`Alert` y `convertPrice` en `web/src/api.ts`; `web/src/alerts.tsx` (`AlertsProvider`); badge en el cabecero (`main.tsx`); página `web/src/pages/Alerts.tsx` con ruta `/alerts`; tarjeta de alertas en `ProductDetail.tsx`; badge de alertas en la tarjeta del `ProductList`.
- Búsqueda y filtros en `ProductList.tsx` con lógica pura en `web/src/productFilter.ts`.
- Script `server/scripts/recompute-best.ts` + npm script `recompute:best` para recalcular el histórico.
- Documentación en `README.md` y `AGENTS.md`.

**Out of scope (for future specs):**

- Comprobaciones automáticas programadas (cron/job). Las alertas dependen de comprobaciones manuales.
- Notificaciones por email, Telegram o webhook: solo aviso in-app.
- Precio objetivo por página (por tienda): solo objetivo por producto.
- Gráfico de histórico de precios con `price_checks`.
- Exportación de datos a CSV/JSON.
- Tests de frontend o e2e (no hay runner de tests en `web/`).
- Paginación de la lista de productos.
- Persistencia de sesiones en base de datos.
- Cualquier cambio en el pipeline de scraping.

## Data model

**Base de datos**

```sql
-- supabase/migrations/0004_add_best_currency.sql
ALTER TABLE products ADD COLUMN best_currency text;
ALTER TABLE pages    ADD COLUMN best_currency text;

-- supabase/migrations/0005_price_alerts.sql
ALTER TABLE products ADD COLUMN target_price double precision;
ALTER TABLE products ADD COLUMN target_currency text NOT NULL DEFAULT 'EUR';
ALTER TABLE products ADD COLUMN target_drop_pct double precision;

CREATE TABLE price_alerts (
  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  product_id bigint NOT NULL REFERENCES products(id) ON DELETE CASCADE,
  page_id bigint REFERENCES pages(id) ON DELETE CASCADE,
  kind text NOT NULL CHECK (kind IN ('target', 'drop')),
  price double precision NOT NULL,           -- precio que disparó la alerta (moneda original)
  currency text,
  price_converted double precision NOT NULL, -- price convertido a comparison_currency
  comparison_currency text NOT NULL,         -- target: target_currency; drop: FX_BASE_CURRENCY
  baseline_price double precision,           -- solo drop: comprobación anterior
  baseline_currency text,
  baseline_converted double precision,
  threshold double precision NOT NULL,       -- target: precio objetivo; drop: porcentaje
  threshold_currency text,                   -- solo target
  created_at timestamptz NOT NULL DEFAULT now(),
  read_at timestamptz
);
CREATE INDEX idx_alerts_product ON price_alerts(product_id, created_at DESC);
ALTER TABLE price_alerts ENABLE row level security;  -- sin políticas: solo service_role
-- reset_sequences() se recrea incluyendo price_alerts
```

**Convenciones:**

- La comparición usa `comparison_currency`; los importes originales se muestran siempre tal cual.
- La API devuelve fechas en ISO 8601 con `Z`.
- Las claves de `sessionStorage` del frontend: `productList:sort` (ya existe) y `productList:filters` (JSON `{query, store, state}`).

## Acceptance criteria

- [ ] Las migraciones `0004` y `0005` están aplicadas: existen `best_currency`, las columnas de objetivo, la tabla `price_alerts` y su índice, y `reset_sequences()` incluye `price_alerts`.
- [ ] `npm run verify` pasa (typecheck server, typecheck web, lint 0 avisos, tests) y `npm run build` genera `web/dist`.
- [ ] Los tests del FX cubren conversión, tipo cruzado vía base, moneda sin tasa (`null`) y fallback estático, sin hacer red.
- [ ] Con una página a 100 USD y otra a 95 EUR (tasa 0,92), `GET /api/products` elige la de menor precio convertido y `best_currency` refleja su moneda.
- [ ] `insertCheck` actualiza `best_price`/`best_currency` comparando convertidos y no cambia el mínimo si el nuevo precio solo es menor sin convertir.
- [ ] Un precio en moneda sin tasa no participa en el "Mejor" y `ProductDetail` muestra el aviso "sin tasa de cambio".
- [ ] `GET /api/products/:id` devuelve `fx`, `best_page_id` y los tres campos de objetivo; `ProductDetail` marca como "Mejor" la fila de `best_page_id` y calcula "Diferencia" en la moneda base.
- [ ] Guardar un precio objetivo menor o igual que el mejor precio actual crea una alerta `target` de inmediato.
- [ ] Comprobar una página cuyo precio baja un porcentaje igual o mayor que `target_drop_pct` crea una alerta `drop` con su `baseline`.
- [ ] Repetir la misma condición en menos de 24 h para el mismo producto y tipo no crea otra alerta.
- [ ] `GET /api/alerts` devuelve hasta 100 alertas con `product_name`, ordenadas por `created_at` descendente.
- [ ] `POST /api/alerts/:id/read` marca `read_at` y `POST /api/alerts/read-all` deja el contador de sin leer a 0; ambos responden 204.
- [ ] El cabecero muestra el número de alertas sin leer, se actualiza tras comprobar o guardar un objetivo, y el enlace lleva a `/alerts`.
- [ ] La página `/alerts` (solo autenticada) lista las alertas con el producto, el importe y la fecha, y permite marcar una o todas como leídas.
- [ ] La tarjeta de cada producto en la lista muestra el badge con sus alertas sin leer (oculto si es 0).
- [ ] La tarjeta "Alertas" del detalle guarda precio objetivo, moneda y % de bajada mediante `PUT /api/products/:id`.
- [ ] Escribir en el buscador de la lista filtra por nombre y por tienda; los selects de tienda y de estado reducen la lista y el contador muestra "N de M productos".
- [ ] Una lista sin coincidencias muestra "Sin coincidencias" y no el estado vacío general.
- [ ] Los filtros persisten en `sessionStorage` y se recuperan al recargar la página (igual que la ordenación actual).
- [ ] `ProductList` muestra el "Precio más bajo histórico" con la moneda de `best_currency`.
- [ ] `npm run verify` está en verde tras todos los pasos.
- [ ] `README.md` y `AGENTS.md` documentan las variables FX, los endpoints de alertas y `recompute:best`.

## Decisions taken and discarded

- **Sí:** FX con `open.er-api.com` + caché de 24 h + fallback estático + override `FX_RATES_JSON`. Razón: gratuita, sin clave y cubre monedas exóticas; la app sigue funcionando si la API cae.
- **No:** agrupar por moneda sin convertir. Razón: descartada por el usuario; no permite ranking entre tiendas en distinta moneda.
- **No:** `frankfurter.app` (BCE). Razón: no cubre todas las monedas de las tiendas asiáticas.
- **Sí:** inyectar FX por parámetro (`buildApp`/`createSupabaseRepo`/`RoutesOptions`). Razón: los tests nunca hacen red, ya es la regla del proyecto.
- **Sí:** si ningún candidato tiene tasa, el "Mejor" se elige por precio crudo con su moneda. Razón: ocultar el mejor cuando todo es no convertible sería peor; el detalle avisa con "sin tasa de cambio".
- **Sí:** alertas solo in-app (badge + página `/alerts`). Razón: decisión del usuario; cero infraestructura nueva.
- **Sí:** objetivo por producto + % de bajada. Razón: decisión del usuario; el objetivo por página queda fuera.
- **Sí:** dedupe de 24 h por producto y tipo. Razón: evita duplicados en cada comprobación sin dejar de avisar al día siguiente.
- **Sí:** evaluar al guardar: `target` contra el mejor precio actual y `drop` contra las dos últimas comprobaciones de cada página. Razón: el usuario ve resultado inmediato; decisión del usuario.
- **Sí:** evaluar las alertas después de `Promise.all` en "Comprobar todas". Razón: una sola consulta de dedupe, sin carreras.
- **Sí:** los importes de la alerta se guardan convertidos (`price_converted`, `baseline_converted`). Razón: el histórico debe reflejar la comparación del momento, no las tasas actuales.
- **Sí:** filtros en cliente sobre la lista ya cargada. Razón: `GET /api/products` ya devuelve todo; sin endpoints nuevos.
- **Sí:** script `recompute:best`. Razón: los `best_price` históricos se calcularon sin convertir y quedarían mal.
- **No:** columna `message` en `price_alerts`. Razón: el frontend compone el texto con `formatPrice`, como el resto de la UI.
- **No:** tests de frontend. Razón: `web/` no tiene runner de tests (regla de AGENTS.md).
- **No:** comprobaciones automáticas. Razón: descartadas por el usuario; si se quieren, van en su propio spec reutilizando la misma evaluación.

## Identified risks

| Riesgo | Mitigación |
|--------|------------|
| La API de tasas no responde o cambia de formato | Fallback estático + `FX_RATES_JSON`; la app sigue comparando y solo se pierden tasas nuevas. |
| Moneda sin tasa (p. ej. VND) | No participa en el "Mejor"; el detalle muestra "sin tasa de cambio". |
| Checks concurrentes crean alertas duplicadas | La evaluación ocurre tras `Promise.all` con una única consulta `hasRecentAlert`. |
| El usuario espera avisos sin comprobar nada | Limitación documentada en README; las comprobaciones automáticas son otro spec. |
| Migraciones en producción con el servicio desplegado | Columnas nullable y tabla nueva; `apply_migration` antes del deploy, sin pérdida de datos. |
| Histórico con `best_price` mal calculado por monedas | Script `recompute:best` ejecutado una vez tras el paso 10. |

## What is **not** in this spec

- Comprobaciones automáticas ni trabajos programados.
- Avisos por email, Telegram o webhook.
- Precio objetivo por página/tienda.
- Gráfico de histórico de precios.
- Exportación CSV.
- Tests de frontend o e2e.
- Paginación de la lista.
- Persistencia de sesiones.
- Cambios en el scraper o en la autenticación.

## Final note

Este spec deja la comparación de precios honesta entre monedas mediante tasas convertidas, añade un canal de alertas in-app que se dispara en cada comprobación, y cierra la carencia de búsqueda y filtros en la lista. Todo se hace sin tocar el scraper, sin red en los tests y siguiendo la inyección de dependencias ya existente en `buildApp`.
